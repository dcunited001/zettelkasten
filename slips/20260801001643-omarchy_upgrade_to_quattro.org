** Backup

Just in case, i booted an image and copied the partitions

#+begin_src shell
devoma3=/dev/nvme0n1
devbackup=/dev/sdb

# check the partition table
sfdisk -J $devoma3

# copying the entire 1TB disk to a 2TB disk would take to long, so
# copy the partition table
sfdisk -d $devoma3 | sfdisk $devbackup

# check the new partition table
sfdisk -J $devbackup
#+end_src

Then copy the specific disks

#+begin_src shell
devoma3=/dev/nvme0n1
devbackup=/dev/sdb

# careful with these commands!
echo dd if="$devoma3"p1 of="$devbackup"1 bs=1M status=progress
echo dd if="$devoma3"p2 of="$devbackup"2 bs=1M status=progress
#+end_src

I'm getting about =6.5GB/min=, so this will take about 150 min ... which seems way
too long, but whatever. It could be drivers or something. This is copying over
USB3.

*** Regenerate =UUID='s

+ this would likely make the drive unbootable until the UUIDs are restored, but
  concurrently mountable with the backup source.
+ if doing so, you should backup the UUIDs from the source and =mount= read-only

Doing that risks leaving your linux a bit confused, since the UUIDs are the same
-- esp. if you try to boot from the backup while the source disk is still
plugged in. Gemini says this would remove the partition UUIDs, forcing =sfdisk= to
recreate them. It keeps the GPT label-id in tact...

#+begin_src shell
sudo sfdisk -d /dev/sda \
    | grep -v ^label-id \
    | sed -e 's/, *uuid=[0-9A-F-]*//I'
    | sudo sfdisk /dev/sdb
#+end_src

#+begin_src nix
  hjem.users.dc.xdg.data = {

          Icon=Alacritty
          Terminal=false

          Name=Alacritty
          GenericName=Terminal

          X-TerminalArgTitle=--title=
