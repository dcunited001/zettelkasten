#+begin_quote
"When physical GPU memory reaches a critical threshold, the orchestrator
triggers eviction policies. Inactive or low-priority agent states are either
dropped completely or offloaded to host RAM...."
#+end_quote

Translation:

+ You have more than one GPU and each has a shitton of VRAM.
+ Your compute resources are pooled and the load is dynamic
+ Many users are running many workloads where input (load) can be modeled, but
  can't be known in advance. Contexts are mixed onto compute resources as
  needed.

**** Cache Eviction

+ system maintains an "LRU index" of active agent sessions
  - this means it's advantageous to keep your agents acting
  - There's not much of a benefit to the user to pull them down (and pull their
    KV Cache & context off the host)
  - ... but the operator benefits in token throughput by keeping hot agents on
    the boxes. This is demand-bound, but more cold agents means the same level
    of demand is allocated to service realization (compute) across a wider
    compute supply

as with any cloud service (operating VMs), there are lots of clever ways to
balance load across a fixed compute supply that result in higher ROI (wrt to
server infrastructure). There's always some unutilized portion of a boxes
capabilities, but ideally the boxes run hot. Load-balancing is hard (this is why
it's called an *elastic* compute cloud)

*** 2. ETL Pipeline Analogy

| Extract   | System fetches system prompts, user history, and *vector database* retrieval tools.                             |
| Transform | Tokenization occurs, followed by the =Prefill engine= transforming raw tokens into *KV tensors*.                  |
| Load      | The resulting *KV tensors* are loaded directly into the allocated paged memory slots within the GPU cache pool. |

** Local Agentic Development and =git-repo= indexes

The process described constructs an AST-based graph where:

1. apparently specifying runtime environment details across many subprojects is a
   non-issue
   - the equivalent of specifying LSP environment for a set of 20-200 repos so
     that each is syntactically/semantically evaluated as it should be
2. it would be very beneficial to have each iteration of output graph database
   artifacts be "differentiable"
   - that is, you can identify the deltas between =code.index.1.db= and
     =code.index.2.db= and this is itself a set of sub-graphs (sub-graphs are
     problematic, since they're not actually connected)

This approach actually ends up being a metric shit-ton of graph data, since
LSP/semantic data:

| is convoluted | is environment-specific (sometimes) | has query specification issues |

*** Example 1

The examples are assuming that there's a superproject repo with a =default.xml=
manifest and that =repo sync= will be used.

+ The config files below should probably be bundled with the manifest or in some
  sibling repository (if there were multiple )
+ if the config comes with the manifest, then you already have it (but there
  could be some branching issues, since the =default.xml= repo can be branched)
+ if the config isn't included with the manifest, then this decouples the
  workload specification from the workload itself (thus, it can be specified by
  some other orchestration tool's data)
+ Depending on how frequently the repositories change (or on the nature of
  branching in subprojects), then bundling it in =.repo= would definitely be
  problematic

*** Example 2: Configuring and Generating the TurboQuant Local Index

*** Deep Dive

Suggests four options for "actual real-world things" that do the indexing, other
than [[https://github.com/github/semantic][github/semantic]], which has been retired.

| Tool            | Indexing Mechanism              | Primary Strengths                                  | Agentic Use Case                               |
|-----------------+---------------------------------+----------------------------------------------------+------------------------------------------------|
| *Tree-sitter*     | Incremental CST / AST Parsing   | Universal language support, fast line/byte mapping | Extracting symbols & structural AST chunks     |
| *SCIP*            | Static Graph Compilation        | Precise cross-repo/cross-file symbol resolution    | Resolving cross-repository import dependencies |
| *Stack-Graphs*    | Incremental Scope Graphs        | Zero-config cross-file import binding              | Real-time code editing & symbol tracing        |
| *Aider, Repo-Map* | AST + PageRank Graph Centrality | Token-efficient structural summaries               | Context window optimization for local LLMs     |

+ github.com/stack-graphs is *not* fast (i read the paper)
+ The best options here would be Aider or SCIP, but really _Aider_
